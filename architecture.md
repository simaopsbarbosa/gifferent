# architecture and experiments

## initial stack

- language and build: Swift 6 with an Xcode macOS application project, deployment target macOS 14. the foundation pins Xcode 26.2 (build 17C52) locally and on the `macos-26` CI runner; update both deliberately after verification.
- UI: SwiftUI scenes and controls, including `MenuBarExtra`; the menu bar label uses the static light/dark `MenuBarMark` asset at 16 points with the accessible name `gifferent`. narrow AppKit windows or views where the full-screen selection overlay, floating preview, drag magnifier, global event behavior, or pasteboard needs them. use native accessibility and appearance APIs.
- capture: ScreenCaptureKit for display and window streams, with a display crop for region recording; public Core Graphics permission APIs for preflight and request. keep selection geometry in display coordinates and test scale factors and screen changes.
- hotkeys: a dedicated Carbon `RegisterEventHotKey` adapter with setting persistence and start/stop state. nonexclusive registration cannot detect another app using the same chord, so settings distinguish registered from observed delivery and warn until the user tests the shortcut from another app. duplicate chords within gifferent and system registration errors are rejected immediately.
- pipeline: timestamped frames enter a bounded queue; encoding and optimization run off the main actor; a small temporary workspace holds the active session. preview closure after export and confirmed discard clean up temporary data. on launch after a crash, delete unfinished session data rather than restoring it.
- editing: keep the captured PNG sequence and first validated GIF as immutable sources. apply trim, speed, and loop settings through `GIFEditModel`; encode replacements to separate quota-reserved files. keep the last usable preview visible while encoding, cancel superseded requests, and publish only the latest completed request. copy and save stay disabled until the visible output matches the selected settings. remove abandoned outputs and obsolete replacements without touching exported files.
- loop metadata: forever GIFs carry a loop extension with a zero count. once GIFs omit the loop extension, so playback ends after the encoded frame sequence. ImageIO may report a finite loop count of one when that extension is absent; validate both its metadata and the encoded application-extension blocks before accepting either mode.
- lifecycle: keep completed temporary media while its preview is active, then delete it when the preview closes after export or is discarded. delete orphaned preview media on launch after a crash. preserve exported files. stop a tracked-window recording when the window closes or is minimized, retaining a partial result only when usable frames exist; continue following the window across displays. stop display recording on display disconnect with the same partial-result rule.
- recording frame: place a thin, high-contrast outline outside a region or window boundary with a small `recording` label at its top edge. use a separate overlay excluded from captured pixels, and adapt contrast to light and dark backgrounds.
- the frame uses a transparent, nonactivating, click-through AppKit panel with SwiftUI drawing. add the visible panel to the app's accessibility windows so assistive technology can discover its `recording` label, then remove it when hidden. map region geometry from display-local top-left points into AppKit screen coordinates. track the selected window's live bounds and reposition the panel as the window moves or resizes. full-display capture has no outside edge and does not show the frame.
- encoder decision: the complete [four-profile matrix](Benchmarks/gifski-magick-35-full-matrix-2026-10-24.md) measured Gifski 1.34.0 as the integration candidate for speed, command-stage memory, and high-motion output size. use Gifski's 1–100 quality control, default 90, as approved by the architect. search resolution, sampled frame rate, and quality; Gifski owns palette generation. the approved quality floor and its sample review status are recorded in [decisions.md](decisions.md). the [four-profile still review](Benchmarks/reviews/encoder-visual-matrix-2026-10-24/index.html) does not assess temporal flicker. keep exact `gif-dispose` package notice, active dependency texts, corresponding source delivery, pinned build, and final-bundle audits as release blockers. ImageMagick is not selected; its measured performance and distribution evidence remains documented for comparison. `gifsicle` remains research-only while its GPL-2.0-only distribution question is unresolved. the native ImageIO path remains the original-GIF implementation, not a compression fallback.
- tests: Swift Testing or XCTest for logic and component integration, XCTest UI tests for acceptance, and fixture-based real CLI tests. keep adapters injectable so tests can control time, capture frames, files, and subprocess outcomes. the foundation uses a debug-only AppKit test window to show the same SwiftUI menu content because hosted CI exposes a zero-size status item that XCTest cannot click. selection UI tests use a synthetic display snapshot in debug test mode, without requesting screen access. verify actual menu bar, permission, hotkey, and overlay interaction on a real Mac. neither test seam runs in normal launches.
- checks: `swift-format`, `xcodebuild`, and GitHub Actions on macOS. release automation signs the app and nested tools, notarizes the artifact, and verifies a clean-machine launch.

## current implementation boundary

the GIF edit transform applies a validated frame range, a speed from 0.5× to 2× in 0.1× steps, and forever or once loop intent to captured PNG frames. the preview's two timeline handles, speed control, and loop control update the export source through this model. replacement encoding keeps the previous preview visible and disables copy and save until the newest request has passed metadata validation. the original GIF and captured frames remain available while edited outputs are replaced within the session quota.

compression has a testable injected `GIFCompressing` boundary and preview lifecycle. the approved integration candidate is the pinned Gifski 1.34.0 CLI, with quality from 1 to 100 in one-point steps and a default of 90. the preview offers GitHub (9 MB target / 10 MB published maximum) and Discord (18 MB target / 20 MB non-Nitro published maximum) targets plus original/75%/50%/25% scale. the displayed maximum scope and research date come from the [destination limits note](Benchmarks/destination-limits-2026-10-24.md). the CLI adapter decodes and scales source frames through ImageIO, writes them in a private temporary directory capped at 128 mib and 32 million pixels, streams Gifski output through a byte-capped pipe, and checks the complete output metadata before accepting it. it derives one `--fps` value and accepts a schedule only when the original timing quantizer confirms that rate reproduces every frame delay exactly; this includes canonical 24 fps 4/5-centisecond cadence, proven against the pinned CLI. irregular schedules are rejected. the adapter never relaxes the coordinator's frame-count, timing, dimension, loop, and size checks. runtime enables compression only when an executable named `gifski` is present in the app bundle. no binary is included by this source change, so normal builds still show compression as unavailable. the app can return to the untouched original preview after compression; failures and cancellation clean pending output. automatic size-goal search and its explicit sampled-frame schedule remain in progress. direct distribution stays blocked until license, source-delivery, build-provenance, and final-bundle gates pass.

recording settings use a separate window opened from the menu. the cursor preference is stored in `UserDefaults`, defaults to included, and is passed into the capture stream for each new recording. the deterministic recording fixture receives the same preference so UI acceptance can verify that the setting reaches capture startup.

while recording, a main-actor warning monitor checks elapsed time and the coordinator's accounted workspace bytes. it presents the first threshold reached: 30 seconds or 75% of the 512 mib session quota. workspace-byte updates are coalesced to at most four main-actor publications per second. the menu-bar warning is non-modal, dismissible, and does not call the recording coordinator; display and region streams exclude gifferent, while selected-window streams contain only the chosen window. deterministic policy tests cover both thresholds, once-per-recording, and dismissal; UI acceptance forces both warning paths and verifies capture remains active.

the recording iteration connects the menu and `⌃⌥R` action to a ScreenCaptureKit stream, bounded newest-frame transport, target-loss monitor, and quota-limited temporary workspace. the workspace is private under the user's cache directory, capped at 512 mib per session, and preserves at least 64 mib of free space. launch cleanup removes orphaned recording sessions; selecting a target from the record action starts capture immediately, while `select capture…` only stores a selection. region targets retain their selected display geometry and are checked against the current display before stream startup; window capture scales resized content to its initial output size. stream preparation is separate from capture start, so the coordinator installs one sequential PNG frame consumer before samples can arrive. concurrent stop requests share one finalization task, which finishes frame delivery, drains the consumer, and then retains usable user-stopped or target-loss sessions. permission loss, stream failure, and frame processing or storage errors discard the session and report failure. after a usable stop, the coordinator validates the ordered PNG sequence, encodes a GIF candidate off the main actor, reads back its metadata, and opens one accessible floating SwiftUI preview. encoding failure retains the captured frames for retry or discard. the preview shows animation, file size, duration, and dimensions; `⌘C` writes the public GIF pasteboard type and `⌘S` opens a save panel. export operations are injectable; closing during an export is blocked, while confirmed discard cancels an in-progress edit and cleans its pending outputs. successful export retains its destination when the preview closes; confirmed discard removes the temporary session. pasteboard write success only confirms the local write, not compatibility with a destination. deterministic UI tests use synthetic frames and fake export adapters without screen permission. real animated paste into GitHub, stream behavior, frame exclusion, window movement and resizing, and encoder candidate performance and quality still need acceptance verification.

## performance experiments before choosing a pipeline

1. build representative fixtures: mostly static UI, fast scrolling, video-like motion, small region, full display, ten seconds, and thirty seconds. include light/dark UI and fine text.
2. compare streaming encode during recording with encode after stop. measure stop-to-usable-preview, CPU, memory, temporary bytes, final GIF bytes, and dropped frames. the under-two-second preview goal may require incremental encoding; prove it on the [selected performance reference](Benchmarks/environment.md), recording its actual configuration for each run.
3. compare complete `gifski`, ImageMagick, and native ImageIO paths at equal output dimensions and frame timing. the full matrix is now recorded; Gifski is approved for backend integration. the native ImageIO app seam remains the original-GIF encoder, not a compression fallback. keep a `gifsicle` path research-only until its distribution license is resolved. inspect text legibility, temporal artifacts, and quality changes alongside bytes and time.
4. measure size-goal search: try the cheapest transformations first, cache intermediate results where safe, stop when the result meets the target, and cap work so the UI never looks frozen. the search order is an experiment, not a fixed requirement.
5. measure the overlay and magnifier at 1× and 2× scaling, with separate displays, and verify that the overlay cannot enter captured frames.

## design constraints

- 24 fps is the initial target, not a guarantee of every system or scene. preserve honest timing and report dropped frames in diagnostics.
- display and region streams exclude gifferent's application in their ScreenCaptureKit filters. selected-window streams include only the chosen window, so the separate overlay window is outside that filter. do not rely on `NSWindow.sharingType` to omit content; Apple's current documentation marks that setting legacy. verify on a real Mac that the overlay never appears in captured frames.
- the quality slider directly controls Gifski `--quality`. size search may adjust sampled frame rate and resolution; Gifski manages palette generation. make the effective settings visible so the result is understandable.
- do not block first preview on secondary optimization if a playable original can appear sooner. show truthful processing state until the final GIF is ready for copy or save.
- avoid automatic capture or background pixel access before the user invokes the recording flow and grants permission.
