# encoder candidate research

research snapshot: 2026-10-24. this is a shortlist and test design, not a tool selection, legal opinion, speed claim, or quality claim. no candidate CLI executable has been bundled or measured in this repository. pin an upstream tag and source commit before building or benchmarking.

the distribution-license screen and required provenance evidence are summarized in [encoder license audit](encoder-license-audit.md). it is not legal advice or a release clearance; the exact source revision, build, dependencies, and binary still require review.

## shortlist

| path | upstream evidence | reason to measure | distribution and product risks |
| --- | --- | --- | --- |
| PNG frames → `gifski` CLI | [manifest](https://github.com/ImageOptim/gifski/blob/main/Cargo.toml) declares `AGPL-3.0-or-later`; [README](https://github.com/ImageOptim/gifski/blob/main/README.md#from-png-frames) documents PNG-frame input, resizing, and quality controls. source defaults to quality 90 and exposes `--no-sort`, `--repeat`, motion-quality, and lossy-quality; the binary's default build disables FFmpeg decoding. its source has a timing-documentation mismatch: CLI help says `--fps` has no effect for PNG, but the PNG decoder uses the supplied rate to timestamp each retained frame ([CLI arguments](https://github.com/ImageOptim/gifski/blob/main/src/bin/gifski.rs#L1628-L1796), [PNG decoder](https://github.com/ImageOptim/gifski/blob/main/src/bin/png.rs#L308-L352)). verify timing using the exact pinned executable and decoded output. there is no explicit numeric dither-strength option in the CLI. | direct PNG-to-GIF path with a top-level license matching gifferent's selected license. | audit the pinned `Cargo.lock`, default and optional features, transitive licenses/notices, modifications, and corresponding source availability. the [publisher's pngquant notices](https://gif.ski/license.html) and [libimagequant license](https://github.com/ImageOptim/libimagequant#license) need review for the exact build. quality, motion-quality, and lossy-quality are not a documented dither-strength slider; treat them as separate controls. |
| PNG frames → `magick` CLI | ImageMagick's [license](https://imagemagick.org/license/) permits redistribution and combining with other licenses, requires its full license and clear attribution, and says modified files need prominent notices; source redistribution is not required by that license. [CLI options](https://imagemagick.org/command-line-options/) document GIF output, per-image `-delay`, Floyd–Steinberg/Riemersma dithering, and `-define dither:diffusion-amount=35%`. | complete PNG-to-GIF path with output animation optimization and a documented numeric diffusion-amount control. | inventory the pinned build's dynamic libraries, coders, delegates, configuration, notices, architectures, and export classification. use a restrictive [security policy](https://imagemagick.org/security-policy/) and verify the diffusion setting changes output for the selected GIF path; documentation alone does not establish it works in every build/configuration. |
| PNG frames → ImageIO GIF → `gifsicle` CLI | Gifsicle's [README](https://github.com/kohler/gifsicle#copyrightlicense) declares GPL version 2 only and also provides an alternative license that requires permission for proprietary distribution; its [manual](https://github.com/kohler/gifsicle/blob/master/gifsicle.1) describes GIF inputs/outputs, per-frame delays, loop settings, optimization, palette controls, dithering algorithms, and lossy compression. | useful optimizer/quantizer comparison, but the full path includes ImageIO GIF creation. Gifsicle does not accept the fixture's PNG sequence as encoder input. | do not link or copy its code. bundling a GPL-2-only executable with an AGPLv3 app needs a legal review of whether the arrangement is separate aggregation or a combined distribution; the README's alternative license requires contacting the author for a proprietary product and is not blanket permission. `--dither` selects an algorithm; the documented surface is not a numeric dither-strength control. include required license/notices if distribution is approved. |

no release encoder is selected by this memo. measure gifski and ImageMagick as complete PNG-to-GIF paths; include ImageIO and ImageIO followed by Gifsicle as comparison paths, with the latter's distribution status unresolved. an existing `ffmpeg` on a developer machine is not a release dependency or measured candidate for this decision; do not enable optional FFmpeg support in the gifski build under evaluation.

the app now has an isolated `OriginalGIFEncoding` interface and a native ImageIO candidate that consumes a stopped workspace's ordered PNG URLs and capture timestamps. it applies cumulative centisecond boundary rounding, uses the preceding capture interval for the final frame (or 1/24 second for one frame), and validates decoded dimensions, count, each delay, infinite looping, and reserved output size. this is only a testable implementation seam: recording does not call it, and it does not satisfy the encoder decision or visual quality gate. the offline harness remains the comparable path for candidate measurements; keep its schedule and this timing policy aligned when the app path is benchmarked.

## candidate discovery and invocation

first record whether exploratory tools already exist; do not install or bundle them as part of this research:

```sh
command -v gifski magick gifsicle
gifski --version
magick -version
gifsicle --version
```

upstream documents `brew install gifski` and provides release executables; ImageMagick documents Homebrew installation; Gifsicle documents source builds with `./configure && make`. these are discovery/prototype routes only. do not use a package-manager binary as release evidence; pin source, recipe, dependencies, architecture, configuration, and checksum for any measured build.

for a direct gifski trial, pass an explicit ordered list of PNG paths, `--no-sort`, `--quality 90`, `--fps 24`, `--repeat 0`, and `--output out.gif`. the PNG decoder implementation appears to set per-frame timestamps at `index / fps`, but the CLI help contradicts that behavior; record the exact binary's help and verify decoded frame delays. ImageMagick's delay is a per-image option in centiseconds by default; generate the expected alternating delays from the fixture schedule and place each delay before its corresponding PNG. apply `-loop 0` after all input frames. compare its normal output with `-layers Optimize`. Gifsicle accepts GIF files and supports optimization, `--colors`, `--dither[=method]`, and `--lossy`; it can set per-frame delays in hundredths of a second. run it only after ImageIO has produced the input GIF, so the comparison includes that full two-stage path. the current ImageIO harness baseline exposes no dither parameter.

the [harness guide](README.md) implements the five-path primary matrix as its default: gifski; ImageMagick without layer optimization; ImageMagick with `-layers Optimize`; ImageIO; and ImageIO followed by Gifsicle. `imageio-app` is an optional sixth comparison that is excluded from the 160-run primary matrix. missing tools such as Gifsicle are marked unavailable with the missing executable named; the harness does not install tools. use the guide's fixture-generation commands, keep output media ignored, and place only checksums, reports, commands, and small approved comparison crops in reviewable evidence.

distribution builds must be self-contained on a clean supported Mac, with all executable code, libraries, helpers, and required configuration inventoried. [Apple's distribution signing guidance](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/) requires distribution-signed code before notarization; [Apple's signing guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html) says to sign nested code first and the app last. Apple's current guidance says use `--deep` for verification, not as a substitute for signing each component. test the notarized app with no Homebrew or developer tool installation.

## benchmark inputs and execution

1. generate the four published 640×360, 240-frame, 24-fps profiles from [`generate_fixture.py`](generate_fixture.py): mixed (default), mostly-static-ui, fast-scrolling, and high-motion-gradient-cursor. use seed 7. generated media belongs under ignored `Benchmarks/generated/`; outputs belong under ignored `Benchmarks/outputs/`. never use private screen content in committed evidence.
2. pin source tags **and commit hashes**, dependency lockfiles, compiler versions, build options, macOS minimum target, binary SHA-256, `file`/`lipo` architecture output, linked libraries (`otool -L`), `--version`, and help output. record the ImageMagick policy and configuration paths. use binaries built for the intended distribution; a Homebrew binary is only an exploratory prototype.
3. run this primary matrix on the selected M2 reference machine: 4 fixture profiles × 5 paths (gifski; ImageMagick without optimization; ImageMagick with `-layers Optimize`; ImageIO; ImageIO plus Gifsicle `--optimize=3`) × 1 cold and 7 warm runs, alternating path order per profile. this is 160 measured path runs. include PNG staging, process launch, encoding, optimization, equivalent ImageIO per-frame metadata inspection, shared structural and fixture-contract validation, and cleanup in end-to-end time; also record component times. the app ImageIO candidate performs its metadata inspection inside its encode call; other candidates use the benchmark helper's `--validate` mode after their final output is produced. this metadata inspection does not force pixel decoding. Gifsicle remains an exploratory row until distribution review allows a packaged test. each output must preserve dimensions, animation frame count, centisecond schedule, cumulative duration, and infinite-loop behavior before it counts.
4. make one cold run, then at least seven warm runs per path on the same named Mac, OS, power mode, and thermal state. run paths in alternating order to limit heat/order bias. retain every raw sample; report median and p90 with the sample count. use separate process sampling for peak resident memory and CPU, and measure the largest temporary directory size during each run. record start-to-preview and stop-to-preview separately from total encode time when pipeline integration exists.
5. after the primary matrix, run a one-warm-run control screen on all four profiles: gifski quality 70/90/100; ImageMagick diffusion amounts 0/35/70 percent (check accepted values and output effect against the pinned build); Gifsicle dithering off, Floyd–Steinberg, Atkinson, and ordered. keep resize, frame rate, palette size, and all other controls fixed within each sweep. the current ImageIO harness baseline has no dither setting. do not equate different tools' numeric quality values. record output bytes, decoded frame count, dimensions, per-frame delays, total duration, loop behavior, first preview readiness when integrated, and any frame merges. visually inspect identical frame indices at 1× and 2× for tiny text, flat UI edges, gradients, color shifts, temporal noise, cursor trails, and flashing. recommend the high-motion-gradient-cursor profile for the first quality-floor review because it exposes gradients, cursor edges, motion, and temporal dithering artifacts; review mostly-static-ui separately for text legibility. keep quality-floor choice with the architect.
6. test cancellation at launch, mid-encode, and during optimization; full disk, malformed frame, missing frame, nonzero exit, and interrupted output. prove bounded memory and temporary disk use, no stale temporary media, and no readable output being mistaken for a finished GIF. repeat on an Intel Mac if Intel distribution is in scope, and always verify the macOS 14 minimum on a real supported Mac.

GIF delays have centisecond granularity, so 24 fps cannot be represented by the same integer delay on every frame. validate the decoded per-frame schedule and cumulative duration rather than assuming a CLI's fps or delay syntax preserves 24 fps. gifski's current source implementation and CLI help disagree about PNG `--fps`, so this is an explicit pinned-binary validation. the final trim/speed/loop implementation must use the same timing contract as its preview.

## result record for each run

record a row containing: candidate/path; source revision and binary checksum; fixture manifest checksum; exact argument array and environment; run order and cold/warm state; elapsed time and first usable preview time; peak resident memory, CPU, and temporary disk; output bytes; decoded duration, frame count, dimensions, and loop value; exit status and validation result. attach the raw measurements, commands, visual samples, and reviewer notes to the benchmark result. choose a candidate only after both credible full paths have results on the agreed reference Mac and the distribution audit passes.

## release audit before bundling

- freeze and archive source revisions, `Cargo.lock` or equivalent dependencies, build recipes, full license texts, copyright notices, modified-file notices, and corresponding source access for any copyleft binary. review transitive licenses rather than inferring them from the top-level license.
- inspect every nested executable, dynamic library, and configuration file in the app bundle. build for required architectures and macOS 14. Apple [distribution signing guidance](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/) requires distribution signing before notarization; sign nested code individually from the inside out, then the app, verify the finished bundle, [notarize](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) the final distribution, and install and launch it on a clean Mac without Homebrew or developer tools.
- confirm that the CLI processes only app-generated local paths and emits no network traffic. pass arguments as an array, never through a shell; use a restricted temporary workspace, bounded resources, and explicit cancellation.

the [benchmark machine](environment.md) is selected and the minimum visual quality floor is approved; representative review evidence and measured results remain gates in [`decisions.md`](../decisions.md). this research may narrow the candidates, but it cannot close those gates.
